# Dependency management

Dependencies are kept up to date by [Renovate](https://docs.renovatebot.com/), configured in
[`renovate.json`](../../renovate.json) at the repository root.

This document explains what Renovate manages, how versions are pinned, and how dependency
updates are reviewed and merged.

## What Renovate manages

| Ecosystem                       | Files                                                 | Renovate manager                    |
|---------------------------------|-------------------------------------------------------|-------------------------------------|
| Python runtime dependencies     | `requirements.txt`                                    | `pip_requirements`                  |
| Python test dependencies        | `requirements-dev.txt`                                | `pip_requirements`                  |
| npm dependencies + lockfile     | `frontend/package.json`, `frontend/package-lock.json` | `npm`                               |
| Docker base images              | `Dockerfile`                                          | `dockerfile`                        |
| Docker Compose images           | `docker-compose.yml`                                  | `docker-compose`                    |
| GitHub Actions                  | `.github/workflows/*.yml`                             | `github-actions`                    |
| Dockerfile apt package versions | `Dockerfile`                                          | `customManagers:dockerfileVersions` |
| SonarCloud Python version       | `.sonarcloud.properties`                              | custom `regex` manager              |
| Pyright Python version          | `pyrightconfig.json`                                  | custom `regex` manager              |
| Ruff Python version             | `.linter-rules/.ruff.toml`                            | custom `regex` manager              |
| Dev Container features          | `.devcontainer/devcontainer.json`                     | `devcontainer`                      |
| Dev Container base image        | `.devcontainer/Dockerfile`                            | `dockerfile`                        |

The standard `config:recommended` preset provides the managers for the main dependency
ecosystems above. A custom Renovate manager is also enabled for
pinned versions of apt packages in the `Dockerfile`.

The Dev Container's features, base image and runtime versions are managed too. Only its npm
linters and `mise` tools float. See
[Pinned and floating dependencies](#pinned-and-floating-dependencies).

Currently, `curl` is pinned in the `Dockerfile` so that its version can be tracked and updated
by Renovate. This allows the Dockerfile dependency to receive a normal Renovate PR rather than
floating to whatever version happens to be available from the Debian package repository at
build time.

## Pinned and floating dependencies

Pin what ships in the production image and what gates a merge. Let the Dev Container's linters
and `mise` tools float to the latest release, with no pins and no lockfiles. The Dev Container's
features, base image and runtime versions are tracked by tag and updated by Renovate, so none of
them needs a manual bump.

| Pinned (Renovate raises PRs)                                            | Floating (Renovate never updates it)                                    |
|-------------------------------------------------------------------------|-------------------------------------------------------------------------|
| `requirements.txt`, the `Dockerfile` base images and apt pins           | `mise.toml` tools, set to `latest`, with no `mise.lock`                 |
| `frontend/package-lock.json`, including the build chain devDependencies | `.devcontainer/package.json` linters, set to `latest`, with no lockfile |
| `docker-compose` images                                                 | The `mise` image (`latest`)                                             |
| `requirements-dev.txt`, which feeds the required `unit-tests` check     |                                                                         |
| SHA-pinned GitHub Actions and the MegaLinter version                    |                                                                         |
| Dev Container features and base image, by tag (not a digest)            |                                                                         |

Why: the Dev Container exists for local convenience, and MegaLinter in CI uses its own bundled
linter versions, so these versions do not control what CI checks. Dev tooling is also
deliberately not tracked for dependency vulnerabilities, and this applies the same decision
to versions. Pinning those tools only produced constant Renovate PRs and a `mise.lock` that had to be
regenerated by hand.

Trade-offs:

* The `Build and test Dev Container` check can go red when an upstream tool releases something
  breaking, unrelated to the PR. It is not a required check.
* Local tool versions can drift from run to run, and from what CI checks.
* A compromised new release of a dev tool is picked up automatically by the Dev Container
  build, with no review step. This is accepted for local tooling.
* `ghcr.io` and `mcr.microsoft.com` give Renovate no release timestamps, so Dev Container feature
  and base image updates skip the seven-day minimum release age
  (`minimumReleaseAgeBehaviour: timestamp-optional`). The rule is scoped to
  `.devcontainer/devcontainer.json` and `.devcontainer/Dockerfile`, so it does not change the wait
  for production images. The Python runtime group has a separate exception, described below. Those
  Dev Container updates are major or minor, so they need a manual merge, and the
  `Build and test Dev Container` check runs on each one.

Do not add `mise.lock`, `.mise/locks/`, `.devcontainer/package-lock.json` or
`.devcontainer/devcontainer-lock.json` back. `mise.lock`, the npm lockfile and any
editor-generated `devcontainer-lock.json` are in
`.gitignore`, and `renovate.json` lists `mise.toml` and `.devcontainer/package.json` under
`ignorePaths`, so Renovate does not extract them at all. Do not add `.devcontainer/**` back:
a pin in an ignored file is never updated, which is how the Docker-in-Docker feature stayed on
v2 and broke on the Ubuntu 26.04 runner. A test in `app/tests/unit/test_dev_stack_files.py`
fails if `.devcontainer/devcontainer.json` or `.devcontainer/Dockerfile` becomes ignored.
SonarCloud's rule `text:S8564` flags the missing npm lockfile, so `.sonarcloud.properties`
excludes `.devcontainer/package.json` from analysis (`sonar.exclusions`).

## Version pinning policy

* **Python**: exact versions (`==`) are used throughout `requirements.txt`
  and `requirements-dev.txt`.

  The packages that previously used `~=` (`pydantic`, `aiohttp`) were switched
  to `==` at their already-installed versions rather than being upgraded. Every subsequent
  version change therefore becomes a visible, reviewable Renovate PR instead of silently
  floating to a newer patch release at build time.

* **npm**: `frontend/package.json` keeps its existing `^`-range versions, and
  `frontend/package-lock.json` records the exact resolved versions installed.

  The frontend Docker build uses `npm ci` rather than `npm install`, so builds install the
  versions recorded in the lockfile.

  Renovate manages both the `package.json` dependency ranges and the associated lockfile,
  allowing dependency updates to be reviewed as normal pull requests.

* **GitHub Actions**: actions are pinned to the full immutable commit SHA of the release being
  used, with a `# vX.Y.Z` comment retaining the human-readable version.

  For example:

  `actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0`

  `renovate.json` extends `helpers:pinGitHubActionDigests`, so Renovate can maintain these
  immutable SHA pins and keep their version comments synchronised.

* **Docker images**:

  * The `Dockerfile` base images are pinned to both their human-readable
    tag and the SHA256 digest that tag resolves to, using the form
    `image:tag@sha256:digest`.

    The tag identifies the intended version while the digest makes the image reference
    immutable. Renovate keeps the tag and digest synchronised when creating updates.

  * `docker-compose.yml` intentionally keeps
    `tommye123/docker-autoheal:latest` unpinned. This is the project's own published image,
    not a third-party dependency, and the example compose configuration is intended to deploy
    the newest published release when copied by users.

    Renovate is explicitly configured not to manage this image.

* **Dockerfile apt packages**: versions are explicitly pinned where required by the `Dockerfile`
  linting policy. Renovate's `customManagers:dockerfileVersions` manager tracks these pins and
  can create update PRs when newer package versions are available.

## Dependency update policy

Renovate is responsible for **detecting and proposing** dependency updates. It may:

* detect new dependency versions
* create dependency-update pull requests
* update existing dependency-update pull requests
* rebase dependency branches when they fall behind `main`
* maintain Docker image digest pins
* maintain GitHub Actions digest pins
* maintain other configured version and digest pins

For regular dependency updates, Renovate waits at least seven days after a release before
proposing it. `internalChecksFilter: "strict"` makes Renovate skip releases that have not
cleared this window instead of selecting a newer, still-pending release. Security updates
bypass the minimum release age so that vulnerability fixes are not delayed.
The Python runtime group is the exception and has no minimum release age (see
"Python runtime version updates").

Two things run only on Saturdays: regular FastAPI updates (a `packageRules` entry with
`schedule: ["* * * * 6"]`) and lockfile maintenance (`lockFileMaintenance`, Saturdays from
00:00 to 03:59, Europe/London time). Lockfile maintenance is never automerged. Renovate ignores `schedule` for vulnerability-alert
PRs, so a FastAPI security update can still appear on another day.

Renovate automatically merges only **eligible patch updates**, and only once every required
GitHub status check has passed. An update is eligible when:

* it is a patch update (`matchUpdateTypes: ["patch"]`), including patch updates of `0.x`
  dependencies.

Minor, major, digest, pin and security updates that are not also eligible patch updates
still require manual review and merge. Automerge is disabled globally and re-enabled only by
the narrower rule in `renovate.json`.

All other dependency-update pull requests require manual review and merge.

Manual review and merge applies to:

* minor updates
* major updates
* Docker digest updates
* GitHub Actions digest updates
* `pin` updates
* `pinDigest` updates
* security updates that are not eligible patch updates

Automerge is not blanket semver-based: it is limited to the explicit patch rule described
above. Broadening it to other update types should be a separate, deliberate change.

### Frontend toolchain grouping

Vite, Vitest and their plugins have interdependent peer dependency ranges, so updating one
package alone can fail lockfile generation. `renovate.json` extends `group:vite` and
`group:vitestMonorepo` for the recommended Vite and Vitest groupings. A package rule also
groups **major** updates to `vite`, `@vitejs/plugin-react`, `vitest` and
`@vitest/coverage-v8` in `frontend/package.json` into a single pull request. Patch and minor
updates are not part of that group, and unrelated frontend dependencies such as React or
ESLint are not grouped with it. Manual review and merge, the seven-day minimum release age and
disabled automerge apply to the group as usual.

### Vulnerability scanning

Two scanners look at the dependency lockfiles, and each other check has one owner:

| Check                                                                                | Owner                                      | Blocks a PR                                              |
|--------------------------------------------------------------------------------------|--------------------------------------------|----------------------------------------------------------|
| Dependency vulnerabilities in lockfiles, and Dockerfile or Compose misconfigurations | Trivy, run by MegaLinter                   | Yes, through the required MegaLinter check               |
| Code quality, security hotspots, dependency risks and the new-code quality gate      | SonarCloud                                 | Yes, once `SonarCloud Code Analysis` is a required check |
| Fixing vulnerable dependencies                                                       | Renovate, using GitHub's Dependabot alerts | It opens the PRs                                         |

SonarCloud's dependency scan (its "dependency risks") gives a second opinion next to Trivy,
using its own advisory database. The scan is a SonarCloud setting (under Advanced Security), not
something `.sonarcloud.properties` controls, and it needs SonarCloud's Advanced Security
entitlement. If that stops being available, Trivy still covers the lockfiles.

Development tooling has no lockfiles any more (see "Pinned and floating dependencies"), so
neither scanner has anything to read for the Dev Container tools, and they are not tracked for
dependency vulnerabilities. `.linter-rules/.trivyignore.yaml` only holds acknowledged
misconfigurations. Trivy scans `frontend/package-lock.json` for the production dependencies of
the built web UI. By default Trivy does not report devDependencies, and this repository does not
set `--include-dev-deps`, so the build chain's devDependencies are not checked by Trivy.

SonarCloud's dependency scan does list devDependencies from that lockfile, such as
`deepmerge` and `uri-js` pulled in by the build tooling, and can fail the `main` quality gate
with "New dependency risks too severe". These tools run during `npm run build`, before the
generated files enter the production image, so each finding is assessed before it is accepted:
is the vulnerable code reachable during the build, and is a fixed version available, often
through a lockfile update or a major bump of the build tool? A finding with no fix, or with no
build-time exposure, is accepted in the SonarCloud UI with a short reason, for example "no fix
available, not reachable in the build". GitHub's Dependabot alerts can also report them.

Python transitive dependencies are not pinned in `requirements.txt` and there is no Python
lockfile, so a lockfile scan, from Trivy or SonarCloud, only sees the direct dependencies
there. The transitive Python packages and the operating system packages in the built image are not scanned. They are
resolved at build time, and a finding in them is rarely something the project can fix itself.
Renovate keeps the base image and the shipped dependencies current instead.

[`SECURITY.md`](../../SECURITY.md) describes how to report a vulnerability, and states that
development tooling is out of scope for dependency vulnerabilities.

### Python runtime version updates

The Python version is set in five places, and Renovate updates all of them in one pull request:

* `Dockerfile` — the `python` base image.
* `.devcontainer/Dockerfile` — the `mcr.microsoft.com/devcontainers/python` image, tagged like
  `3.14-bookworm`.
* `.sonarcloud.properties` — `sonar.python.version`, used by SonarCloud.
* `pyrightconfig.json` — `pythonVersion`, used by Pyright.
* `.linter-rules/.ruff.toml` — `target-version`, written in the `py314` form.

SonarCloud runs automatic analysis, which reads `.sonarcloud.properties` from the default
branch and ignores `sonar-project.properties`. That file also sets the test file patterns and
source encoding.

Three custom regex managers in `renovate.json` track the pins that are not Dockerfiles. The
SonarCloud pin is found through the `# renovate:` comment immediately above it. The Pyright pin
is found by matching the `pythonVersion` key. The Ruff pin is found by matching `target-version`;
its `currentValueTemplate` rebuilds `3.14` from `py314`, and its `autoReplaceStringTemplate`
writes `py315` back. All three use the `docker` datasource with the dependency name `python`, so
they follow the same releases as the `Dockerfile` image. The Dev Container image is an ordinary
Dockerfile `FROM` line, read by the `dockerfile` manager.

A package rule groups all five updates into one "Python runtime" pull request, so a new Python
version moves them together. The tag formats differ (`3.15-slim`, `3.15-bookworm` and plain `3.15`), but Renovate resolves each to the same release. A new Python version is a minor or
major update, so the grouped pull request needs manual review and merge like any other, and
automerge stays disabled.

The rule sets `minimumGroupSize: 5`, the number of pins Renovate manages. Renovate does not
create the branch until all five have an update available. Fewer than five available updates
create no branch and no pull request, so a partial runtime upgrade cannot be proposed. The
Dev Container image can lag a new Python release, because Microsoft publishes it after the
upstream image, so the pull request may appear later than the `Dockerfile` update alone would.

The seven-day minimum release age does not apply to this group. The likely cause of the group
not forming is that the `python` image tags (`3.15-slim`, `3.15`) are floating tags that the image
publishers rebuild, which restarts the seven-day clock each time. The Renovate log showed the
`Dockerfile` and tool pins held back by the age check while the Dev Container image, which has no
release timestamp, was not. The repeated rebuilds were inferred from Docker Hub timestamps, not
observed. Either way, the pins could not all clear the check together, and the group stayed below
`minimumGroupSize`. The pull request still needs manual review and merge. The rule sits after the
general `minimumReleaseAge` rule in `renovate.json` because later rules win.

Two things to know about the minimum:

* It is a count, not a list of files. If a Python pin is added to or removed from Renovate's
  management, change `minimumGroupSize` to match. Set too high, the group never forms and no
  error is shown. Set too low, partial upgrades are possible again.
* The rule applies to major and minor updates only. Digest refreshes for the existing tags are
  not grouped, so they are not held back by the minimum.

`minimumGroupSize` guarantees how many updates are in the group, not that their target versions
match. Before merging a "Python runtime" pull request, compare the versions in all five files.

The general digest pinning rule is switched off for `.sonarcloud.properties`,
`pyrightconfig.json` and `.linter-rules/.ruff.toml` because those tools need a bare version
number and not `3.15@sha256:…`. It is also switched off for the two Dev Container files, which
float on a tag.

#### Merging a Python runtime pull request

The "Python runtime" pull request changes all five pins, so the unit tests pass without further
edits. A contract test in `app/tests/unit/test_dev_stack_files.py` checks that the `Dockerfile`,
the Dev Container image, SonarCloud, Pyright and Ruff all agree, so a runtime upgrade cannot be
merged with any reference missed. It catches a pin that drifts for any reason, not only through
Renovate. The workflows that run on Python read the version from the `Dockerfile`, so they follow
it automatically.

If you push your own commits to the Renovate branch, Renovate treats it as modified and stops
updating and rebasing it. Bring the branch up to date yourself by merging `origin/main` into it.
Do not tick the pull request's rebase/retry checkbox after editing: Renovate rebuilds the branch
from scratch and discards your commits.

Keep the `# renovate:` comment directly above the `sonar.python.version` line when editing
`.sonarcloud.properties`, or Renovate stops tracking it.

### Node runtime version updates

The Node major is set in four places, and Renovate updates all of them in one pull request:

* `Dockerfile` — the `node` image of the frontend build stage.
* `.github/workflows/tests.yml` and `.github/workflows/production-smoke-test.yml` —
  `node-version` of `actions/setup-node`.
* `.devcontainer/devcontainer.json` — the `version` option of the `node` feature. Renovate's
  built-in `devcontainer` manager reads it, so it needs no custom manager.

A package rule groups them into one "Node runtime" pull request with `minimumGroupSize: 4`. It
matches the dependency name `node` (`matchDepNames`), not the package name, because the
`setup-node` pins have the package name `actions/node-versions` while the `Dockerfile` and Dev
Container pins are named `node`. As with Python, the minimum is a count, not a list of files:
change it if a Node pin is added or removed, and note that set too high the group never forms and
no error is shown. Only major updates are grouped, so digest refreshes are not held back, and a
Node major needs a manual merge. `test_node_runtime_versions_are_aligned` in
`app/tests/unit/test_dev_stack_files.py` fails if the four places disagree.

### Rebasing

`rebaseWhen: "behind-base-branch"` is enabled.

This allows Renovate to keep dependency-update branches current with `main` when the base branch
moves. Keeping branches current means dependency PRs can be tested against the latest project
state rather than remaining based on an increasingly stale commit.

### Semantic commits

Renovate uses semantic commit conventions with the `chore` commit type for dependency updates.

This keeps automated dependency-update commits consistent with the repository's commit naming
conventions.

## Digest pinning

Digest pinning remains enabled and is independent of automerge, which applies only to eligible
patch updates.

Two important Renovate behaviours are retained:

* GitHub Actions are pinned to immutable commit SHAs through
  `helpers:pinGitHubActionDigests`.
* Docker image references can be pinned to immutable SHA256 digests through the
  `pinDigests` rule.

Digest updates are still normal pull requests and require manual review.

Pinning and automerge are intentionally separate concerns: Renovate can maintain secure,
immutable references without being allowed to merge the resulting changes automatically.

## Security updates

Security updates are subject to the same policy as other updates.

A security fix that is an eligible patch update may be automerged once required checks pass.
A minor or major security fix is not automerged and requires manual review.

Security-related dependency PRs therefore receive the same CI validation as other dependency
updates, and human review unless they are eligible patch updates.

Manual review of non-patch security fixes is intentional: security fixes are important, but
automatically merging them can still introduce compatibility or behavioural changes.

## Why some things are left alone

* **The project's own Docker image** — `tommye123/docker-autoheal:latest` is intentionally
  excluded from Renovate dependency management because it is produced by this repository rather
  than being a third-party dependency.

* **Pre-1.0 and build tooling dependencies** — `0.x` patch updates are automerged like other
  eligible patch updates. Build tooling is automerged
  only when its update is a patch. A patch or minor version does not automatically mean a
  dependency is behaviourally risk-free.

* **`checkov` as a Dev Container tool** — it is deliberately absent from
  `mise.toml`. Its findings in this repo are covered elsewhere or deferred: Actions
  permission findings are covered by zizmor, and the Dockerfile non-root finding is deferred
  to issue #2, so Trivy ignores `DS-0002` and Checkov skips `CKV_DOCKER_3`. It still runs in CI
  through MegaLinter's bundled `REPOSITORY_CHECKOV` linter, so CI coverage is unaffected. `semgrep`
  is the one kept in the Dev Container because it catches app-level issues nothing else in
  the local stack checks for.

## Current policy summary

The intended workflow is:

```text
Renovate detects an update
        |
        v
Renovate opens or updates a PR
        |
        v
GitHub Actions runs
        |
        v
CI passes
        |
        v
Eligible patch update?  --yes-->  Renovate automerges once required checks pass
        |
        no
        v
Maintainer reviews the changes
        |
        v
Maintainer approves and merges
```

Renovate may maintain the PR and keep it rebased. Non-eligible updates remain under the
maintainer's final merge decision.

`platformAutomerge` is kept `false` in `renovate.json`, so Renovate performs automerge itself
rather than requesting GitHub's native auto-merge. Renovate merges an eligible PR only when its
branch's status checks are green.

### Required repository settings

Automerge of eligible patch updates depends on these GitHub settings. They are not stored in
the repository and must be verified in the repository's settings:

* Branch protection on `main` requires the mandatory CI status checks, so a PR cannot merge
  until they pass. Do not weaken this to make automerge work.
* Branch protection must not require an approving review for the bot's PR to merge. If it does,
  Renovate cannot complete automerge and those patch PRs wait for a maintainer.
* The Renovate app must be allowed to push and merge in this repository.

### Limitations

* Automerge only runs when Renovate next processes the PR, so a merge may lag a green check.
* Most PRs wait for the seven-day minimum release age before Renovate proposes them. The Python
  runtime group and security updates do not.
* Patch updates that fail CI or depend on an unmerged PR are not merged.

This policy is intentionally narrow while the project's test coverage, integration testing and
CI confidence continue to improve.
