# Documentation drift detection

The **Documentation Drift Detection** workflow audits one focus area of the documentation
against the implementation each week and proposes corrections as a draft pull request. It
does documentation drift only: other maintenance is the Weekly Maintainer's job.

## How it works

- The source of truth is `.github/workflows/docs-drift.md`, a
  [GitHub Agentic Workflow](https://github.github.com/gh-aw/). The compiled
  `.github/workflows/docs-drift.lock.yml` is generated by `gh aw compile`; don't edit it by hand.
- It runs on `workflow_dispatch` only. Call it weekly from cron-job.org, as for the Upgrade
  gh-aw and Weekly Maintainer workflows. It uses Gemini CLI 0.66.0 with `gemini-3.6-flash`
  through the existing `GEMINI_API_KEY` secret. The free tier allows 20 requests a day per
  model, and a run takes five requests without drift, eight with it and ten if the pull request
  cannot be created, so don't run it on the same day as another workflow that uses `gemini-3.6-flash` on the same key, such as the
  Weekly Maintainer once it moves to that model.
- **Focus area.** The last digit of the ISO week number, modulo 5, picks one of five areas.
  Each pairs documents with the source that implements them, and every run also reads
  `README.md`:

  | Area                                 | Documents                               | Source and files                                                               |
  |--------------------------------------|-----------------------------------------|--------------------------------------------------------------------------------|
  | Configuration and deployment         | configuration, installation, migration  | `app/config/`, `app/main.py`, `docker-compose.yml`, `Dockerfile`               |
  | Health checks and recovery           | health checks, labels, maintenance mode | `app/monitor/`, `app/docker_client/`                                           |
  | API, UI and architecture             | usage, architecture, project structure  | `app/api/`                                                                     |
  | Metrics, logging and troubleshooting | monitoring and metrics, troubleshooting | `app/main.py`, `app/config/config_manager.py`, health routes                   |
  | Notifications and Uptime Kuma        | notifications                           | `app/notifications/`, `app/uptime_kuma/`, `app/monitor/uptime_kuma_monitor.py` |

  The table is in `.github/scripts/docs-drift-areas.sh`. Over five weeks every document under
  `docs/user/` and every app source directory that holds code is covered. The developer and
  maintainer documents other than architecture and project structure are not audited yet. A
  unit test fails if a mapped file is renamed or removed, so update the table in the same
  change.
- **Read plan.** A pre-agent step appends the area's files to the prompt as the exact
  `cat -n` commands to run, in three parts. The agent must read the files; a step after it
  checks that it did.
- **Coverage check.** A post-step (`.github/scripts/docs-drift-coverage.sh`) rebuilds the same
  file list from the checkout and the week number (passed on through `GITHUB_ENV`, so nothing
  the agent can write changes it) and counts the successful `cat -n` reads in the agent's own
  tool log against it. If any file was not read in full, it replaces the pull request with a
  no-op and fails the run, so nothing is opened from an incomplete audit. The agent's own claim
  of coverage is not trusted.
- **Editing.** The agent edits documents with `replace`, creates a branch with
  `git checkout -b` and commits only the files it edited with `git commit -m ... -- FILES`,
  then calls the `create_pull_request` safe output. gh-aw builds the pull request from that
  commit (and rewrites its message to "Apply filtered changes", because the workflow sets
  `excluded-files` to keep `.github` out of the patch). If creation fails twice, the run reports an incomplete audit.
- **Evidence.** A correction needs the documentation statement, the contradicting code,
  configuration or test with file and line, and no disagreement between code and tests. Those
  four items go in the pull request for each correction. Uncertain or conflicting cases are
  listed under "Needs human review" and not edited, and at most five corrections are made
  per run.
- **Outcome.** The run page shows one of "Documentation drift found", "No documentation
  drift found" (with at least five claims checked, each with the quoted document and code
  lines) or "Incomplete audit".

## Evidence from grep

The agent reads only its focus area's files, so it cannot see from them alone that a documented
setting is read nowhere. After the reads, in the check turn, it may search `app` and
`frontend/src` (tests excluded) with `grep -rn -- KEY ... | head -n 20` for up to ten setting
keys: bare key names that the documents present as working options and that it saw defined but
not used. A grep can only show where a name appears, never how code behaves. A key counts as
having no reader only if the grep printed fewer than 20 lines (a full 20 may be cut), every
match is a definition, a default or a test, and the code it read has no generic handling
(`getattr`, `model_dump`, a loop over fields, a form built from the model). Then it corrects the
document only to say the option has no effect, and notes under "Needs human review" that the
code may be incomplete. Otherwise it makes no edit and lists the key for review. Environment
variables, routes, labels and metric names are not searched this way, because they are often
built from parts.

## Permissions

The agent job has read-only `contents`, `issues` and `pull-requests` permissions. The only
write path is the `create-pull-request` safe output, applied by a separate job: one draft
pull request titled `[docs] ...`, limited to `README.md`, `docs/user/**`,
`docs/developer/architecture.md` and `docs/developer/project-structure.md`. A patch touching
anything else is rejected, except changes under `.github`, which are dropped from the patch
(gh-aw restores that folder before the run, which can change the mode of scripts in it).
gh-aw treats `README.md` as a protected file, so a pull request that edits it is still
created, with a review comment from gh-aw saying the protected file needs a person's review.
No issues are opened, and nothing is merged automatically.

A pull request created with the default `GITHUB_TOKEN` does not start CI. Run the checks on
it before treating it as ready.

## Running it manually

Actions → **Documentation Drift Detection** → **Run workflow** on `main`, or:

```bash
gh workflow run docs-drift.lock.yml --ref main
```

The area follows the week the run starts in. To audit a particular area instead, pass its
number (0 to 4, in the order of the table above) as the `area` input:

```bash
gh workflow run docs-drift.lock.yml --ref main -f area=3
```

To see which files a week would read, run the read plan script locally; the temporary file it
appends to lists the files:

```bash
plan=$(mktemp); PROMPT_FILE=$plan WEEK=<number> bash .github/scripts/docs-drift-reads.sh; cat "$plan"
```

Review any draft pull request as normal: check each cited piece of evidence, and that only
documentation changed.

## Changing it

Edit `.github/workflows/docs-drift.md`, run `gh aw compile --strict --actionlint` with the
gh-aw version recorded in the header of `.github/workflows/issue-triage.lock.yml`, and commit
both files. The Upgrade gh-aw workflow keeps the compiler version current.
